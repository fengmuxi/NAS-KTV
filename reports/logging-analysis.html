一、现状架构

后端用 pino 输出，经过三层处理：

  • logger.ts：pino({level: LOG_LEVEL||'info'}) → multistream([stdout, createLogTransport()])。stdout 供容器采集；transport 把 JSON 行解析进内存 buffer（上限 5000）。
  • log-service.ts：内存 buffer[] + WS 广播（/ws/logs）+ REST 查询/统计（/system/logs、/system/logs/stats）。
  • request-logger.ts：每个请求 finish 后记录 method/url/status/耗时；≥3000ms 记为 warn（慢请求）。
  • separator-log-poller.ts：每 5s 轮询 separator :8001/api/logs?limit=50，合并进同一 buffer（service=separator）。
  • admin-web Logs.tsx：实时 WS + 历史 REST，支持 服务/级别/时间/关键字 过滤、关键字高亮、统计、自动滚动/暂停。
backend logger ─► stdout (容器采集) ┐
└─► Transport ─► buffer[5000] ─► WS 推送 / REST 查询
separator :8001 ─► poller 5s ─► addExternalEntry ─► buffer ─► 同上

二、关键问题与排查痛点

优先级问题影响根因 / 位置
P0 meta 信息完全不可见 后端 logger.error({err}, msg)、慢请求的 method/url/耗时 等结构化字段，前端 Logs.tsx 只渲染 message，丢掉 entry.meta。错误栈、请求上下文在界面上完全看不到，排查靠猜。 Logs.tsx 列表渲染未读取 entry.meta
P1 日志无持久化 仅内存 5000 条，进程重启即丢；无文件落盘。跨重启/多实例无法回溯历史，线上排障困难。 createLogTransport 只入内存；无 file sink
P1 时间范围过滤的时区 bug 前端 datetime-local（本地时区）作为字符串，与后端 ISO UTC 字符串（如 2026-08-19T02:00:00.000Z）做字典序比较。非 UTC 环境会误判，明明有日志却过滤为空。 前后端时间格式不一致，log-service.queryLogs 用字符串比较
P2 downloader 服务未接入 只有 backend + separator，musicdl 下载服务（:8002）日志看不到，下载失败无从定位。 无 downloader-log-poller；downloader 也未暴露 /api/logs
P2 Separator 轮询去重脆弱 基于单一 lastTimestamp 字符串去重，同一毫秒的多条日志会被丢弃；separator 单次返回上限 50，5s 内超量会被截断丢失。 separator-log-poller.ts 比较 ts <= lastTimestamp
P2 WS 实时流不支持时间/关键字服务端过滤 时间过滤仅在 REST 拉取生效；实时流只按 level/service 服务端过滤，关键字靠前端。停在历史区间时实时流仍推全量。 registerLogClient 仅支持 level/service
P2 级别映射不严谨 + 默认不输出 debug PINO_LEVEL_MAP 把 pino 20(debug)/10(trace) 都映射成 debug，缺 trace；logger 默认 level=info，debug 需 LOG_LEVEL=debug 才出。 logger.ts / log-service.ts
P2 前端高亮用 color-mix(oklch,…) 旧内核/部分浏览器不支持，降级可能失效或对比度异常。 Logs.tsx highlightMatches 内联样式

三、优化建议（按优先级）

P0 — 直接打通排查链路（半天级）

  • 渲染 meta：Logs.tsx 在每条日志下折叠展示 entry.meta（尤其 err 栈、请求元数据），错误条目默认展开或用 <details> 折叠，避免刷屏。
  • 修复时间过滤时区：前端传 epoch ms（Date.getTime()）或后端用 new Date() 比较；不要做字符串比较。

P1 — 补齐可用性与覆盖

  • 接入 downloader 日志：给 downloader FastAPI 增加 /api/logs（仿 separator 的内存 handler），并新增 downloader-log-poller.ts 合并到 buffer，前端服务下拉增加 downloader 选项。
  • 更稳的去重：separator poller 用「时间戳 + 内容指纹」或 lastId 去重，避免同毫秒丢日志；适当提高 limit 或改增量游标。
  • 可选落盘：增加按日滚动的文件 sink（如 pino/file 或写入 data/logs/），或延长 buffer / 持久化到 SQLite，便于重启回溯。

P2 — 体验打磨

  • WS 服务端支持 keyword + 时间过滤，与 REST 拉取一致。
  • 补全 trace 级别、提供运行时调级接口（PATCH /system/logs/level）。
  • 增加「导出 JSON/CSV」按钮，方便贴给排查。
  • 引入 requestId（traceId）贯穿请求链，便于串联一次操作的全部日志。
  • 前端高亮改用纯色背景（如 var(--color-warning) 低透明度），去掉 oklch。

四、落地顺序建议

  1. 先做 P0：改 Logs.tsx 渲染 meta + 修时间过滤 → 立竿见影提升排障效率。
  2. 再补 P1：downloader 接入 + 落盘 → 覆盖全链路、可回溯。
  3. 最后 P2 打磨。

所有改动遵循项目约束：新增 schema 需迁移（本任务多为前端+后端 service，不改表）；前端走 Hallmark 规范；不改历史迁移文件。
